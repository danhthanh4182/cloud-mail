# Android completion and acceptance

This addendum extends T005–T012. It is the test contract for the remaining Android work. Each result requires evidence against the candidate source revision.

| Case | Given and action | Expected result |
|---|---|---|
| AC19 Conversation | Receive a parent, two replies, and another message with the same subject. Open one reply. | The reader lists linked messages in chronological order and expands their bodies inline, using Message-ID, In-Reply-To and References. Results stay within the same user and mailbox. |
| AC20 Message rendering | On Android, open a marketing fixture with nested layout tables and a mobile media query, then a verification fixture with a styled action and an HTTPS image. Repeat at 360 logical pixels in light and dark mode and at 200% text scale. | The marketing layout retains columns where specified and responds to the viewport. The verification action retains its position and confirms the target before opening externally. Data tables retain rows and columns. Wide content scrolls within the message. JavaScript, automatic navigation and unsolicited network requests are blocked. HTTPS images load only after consent for the current message. Protocol-relative and lazy image sources and bounded HTTPS redirects load. If images are unavailable, the reader reports the problem. A short branded email with a full-page root height keeps its footer and native actions close together at both phone and tablet widths. A rendering failure falls back to readable content. |
| AC21 Attachments | Download a file, cancel midway, retry and forward the message with a selected original attachment. | Download stops and reports progress where size is known. The file can be saved after completion. Only selected, owned attachments are forwarded within configured limits. |
| AC22 Draft replication | Save a draft on A, sync B, edit it on both devices and sync again. Also delete a draft while B is offline. | Compatible servers replicate editable text and attachment count. Attachment bytes stay on the originating device. A replica with missing files blocks send until the user reattaches or explicitly removes them. Server revisions prevent lost updates. Both conflicting texts survive, and deletion reaches a clean replica. In-flight send intents retain their original identity and stay local. |
| AC23 Offline changes | Queue a reversible message change while disconnected, reopen, reconnect, and encounter a concurrent server edit. | The encrypted queue remains scoped to the session identity, replays in order, and never changes server state after a revision conflict without a fresh user action. A visible status shows pending changes, last sync and conflicts. Sending is never queued. The client refreshes authoritative mailbox snapshots after replay. |
| AC24 Assistant | Correct a sender category, search with an ordinary-language sentence, and request a reply to a message. | The saved sender rule wins over deterministic classification. The app previews editable search filters. Reply text is a draft suggestion and requires review and explicit send. Mail data is bounded and redacted before hosted model calls. |
| AC25 Android push | With matching Firebase configuration, grant permission, trigger an incoming message, tap the notification, then sign out. Repeat with denial and a different signed-in account. | Generic notification text carries no sender, subject, body or OTP. A tap opens only mail owned by the current session and matching its installation registration. Denial is visible. A scoped Android job renews SDK-rotated tokens. Sign-out removes local notification state and revokes the registration when the Worker is reachable. |
| AC26 Server compatibility | Point the app at a Worker without the new D1 migration and use Starred filters. | Existing read flows still operate. Unsupported actions and filters are clearly disabled. The updated Worker applies Starred query, address and dates at the server before paging. |
| AC27 Release | Build the exact PR revision and run the device checklist on Android. | CI attaches an APK, signature, manifest, source revision and checksum. Android integration, live-provider, accessibility and production-signing results are reported separately. A debug artifact cannot satisfy the production signing gate. |
| AC28 Message identities and labels | Open a labeled message with named and unnamed To/Cc recipients. Repeat with a confirmed DMARC pass, an older message and a message with forged authentication metadata or a lookalike sender name. | The sender address and initials are visible. Expanding recipients shows names and addresses when available, with initials generated locally. Labels appear in the reader and a bounded preview appears in the mailbox list. Only the server-confirmed receiving-gateway result displays a domain-authentication badge. The explanation names the domain and the scope of DMARC. Older messages without evidence open normally. |
| AC29 Parallel Android installation | With Cloud Mail already installed and a local draft present, install the Preview from GitHub Actions. | Android lists a second launcher entry named Cloud Mail Preview. The original app retains its sign-in and local draft. Preview asks for its own sign-in. CI verifies that the preview manifest uses the `.preview` package and that signed releases use the canonical package and configured certificate. |

Automated tests cover deterministic and isolated integration cases. Physical device, live FCM and provider tests require a controlled mail deployment and a matching Firebase project. Record whether each test was executed, passed, failed or blocked in [QA evidence](qa-evidence.md).
